Proposal Studio: from RFP to proposal deck, on your own machine

Proposal Studio is a local, offline workbench for pre-sales solutions architects. You attach an RFP in a chat window and get cited answers, a structured digest, a tailored deck, and finally a PowerPoint on your firm's template. Nothing leaves your laptop.

📄 Understand the RFP

Ask questions and get answers with [section, p.N] citations, or a plain "Not found in the RFP."

🧭 Digest it

Problems, before/after, requirements, evaluation criteria, compliance and risks, all cited, plus an Excel requirements matrix.

🧱 Reuse what works

Harvest anonymised content blocks from past proposals, curate them, and let the writer tailor them to each RFP.

🖼️ Render on your template

A deterministic PowerPoint renderer (no AI involved) with a QA report: truncations, empty placeholders, missing sources.

🔎 Research offline

Multi-step research across your library and the RFP, written up as a cited markdown report.

🤖 Sandboxed agents

Hand file tasks to local agent CLIs with plan → approve → apply → approve, inside a sandbox.

How to read this tutorial Set it up once (sections 1–4), then follow Your first proposal with the built-in synthetic RFP. All examples use fictional organisations ("Acme Health Plan", "Example Hospital") and real output from the default local models.

How it works

Three local pieces work together. The Proposal Studio app is the chat window in your browser (studio ui). Ollama runs the AI models on your machine. The studio Python package does the actual work, and it's the same code whether you use the app, the terminal chat or the CLI.

Design principles you'll notice

  • The router is code, not an agent. Plain Python decides what runs. You always see why: every reply starts with a line like → routed to /ask (rules).
  • AI does only narrow jobs: extracting facts, tailoring a slide, answering a question. Formatting, rendering, citations and checks are all deterministic Python.
  • Everything is cited. Answers, digest items and slides carry their sources, and the renderer puts them in the speaker notes.
  • Nothing writes files behind your back. Rendering, harvesting and agents only run when you type the command or approve.
  • Small models, honest output. When something can't be supported by your blocks or the RFP, it's flagged for review, not invented.

1Install

Get the code: either download proposal-studio-<version>-windows.zip from the GitHub Releases page and unzip it, or clone the repository. Then run the setup script once, while online. It's safe to run again; it only does what's missing.

cd proposal-studio
powershell -ExecutionPolicy Bypass -File scripts\setup.ps1

"ExecutionPolicy Bypass" applies to this one run only and needs no admin rights.

cd proposal-studio
scripts/setup.sh

The script:

  1. Creates a Python virtual environment in .venv (using uv if you have it).
  2. Installs the studio package into it.
  3. Starts Ollama if needed and pulls the three models listed in config/models.yaml.
  4. Prints a list of anything it couldn't do (for example "Ollama not found"), so you can fix it and re-run.

2Start it

From now on you can be offline. Start Proposal Studio with:

Windows
powershell -ExecutionPolicy Bypass -File scripts\start.ps1
macOS / Linux
scripts/start.sh

Your browser opens Proposal Studio at http://127.0.0.1:8765/?t=…. That link unlocks the app for this session (a new one each launch), so keep it private. If you close the tab, open the link from the terminal again.

The start script applies scripts/offline.env every time:

  • Ollama with cloud features off and one model loaded at a time (it matters on 16 GB);
  • no telemetry from any library;
  • the app itself listens on 127.0.0.1 only and loads nothing from the internet.
Windows: quit the Ollama tray app first If Ollama is already running from its tray icon, it won't pick up the settings above. Quit it (right-click the icon → Quit), then run start.ps1, which starts Ollama with the right settings.

3Projects & folders

A project is one bid, and it lives in a folder you choose and trust. Click New project, give it a name and tick I trust this folder. By default a new folder is created at Documents\Proposal Studio\<project name>. Use Choose another folder… to put it anywhere, including a folder that already holds your bid documents. Proposal Studio reads and writes only inside it.

In a project folderWhat's there
input/The RFP files you uploaded.
out/Rendered PowerPoint decks and requirement matrices.
chats/The project's chats.
digest.json, deck.jsonThe RFP summary and the slide content.

Each project shows its path in the sidebar, and in full at the top of the Files tab with Open folder. Settings (the sliders icon at the bottom of the sidebar) shows the Proposal Studio folder. It holds your shared library of past proposals, reference documents and content blocks.

Everything you create can be removed. In the ⋯ menu next to a project, Remove from list keeps the folder and Delete project and its folder deletes it. Chats and files have their own delete buttons.

Find your way around

  • Sidebar: projects and recent chats. Ctrl/⌘+B collapses it to icons.
  • Side panel: Files, RFP summary and Slides for the open project. Ctrl/⌘+J shows or hides it; drag its edge to make it wider.
  • Models: click the model status at the bottom of the sidebar to see what's installed, what's loaded, what fits in memory, and to choose which model does what.

Your first proposal

The whole flow, which the rest of this tutorial goes through step by step:

/new→attach RFP→ask→/digest→/outline→/deck→/edit→/render

To practise without real documents, generate the synthetic Acme Health Plan RFP:

.venv/bin/python -m studio.samples acme-fixtures   # writes acme_rfp.pdf, .docx, .xlsx, .pptx

In the app, just drop the RFP onto the home screen. A project (one per RFP you're bidding on) is created and named after the file, and the file is read right away. You can type a question in the same message. The slash commands below still work, and they're what the rest of this tutorial shows, because they make each step explicit. In the app, the Analyse RFP and Build slides buttons run the same steps.

You

Ingest an RFP

Attach the RFP file(s) with the paperclip and send. A message with only attachments routes to /ingest automatically.

You
📎 acme_rfp.pdf
PS
→ routed to /ingest (rules)
Reading acme_rfp.pdf… · Embedding 9 chunks…
new: acme_rfp.pdf
Indexed 9 new chunks (9 total).
Next: ask a question, e.g. "When are proposals due?", or /digest
  • Supported formats are PDF, DOCX, XLSX, PPTX, TXT and MD. Headings and page/slide numbers are kept for citations, and tables are read row by row with their headers.
  • Re-ingesting is incremental: unchanged files are skipped.
  • Use one format per document. The same RFP as both PDF and DOCX gives duplicate excerpts.
PHI check Every file is scanned for things that look like patient data (SSNs, MRNs, dates of birth, names with phone numbers). If anything turns up, nothing is ingested. You see the file, page and kind of match (masked), and can confirm with /approve only if it's a false positive. RFPs should never contain PHI.

Behind the scenes the model cites excerpt numbers, and Python turns them into exact [section, p.N] labels, because small models copy long labels badly.

The RFP digest

/digest reads the whole RFP in chunks and builds a structured, cited summary: the opportunity facts, business and technical problems, today vs. wanted, requirements, evaluation criteria, compliance, systems, risks and questions to ask the client. Add xlsx for a requirements compliance matrix you can download.

You
/digest xlsx
PS
→ routed to /digest (command)
## RFP digest — Enterprise AI Platform
- Client: Acme Health Plan
- Due: March 15, 2027
- Submission: via the Acme procurement portal
- Limits: 30 slides

### Requirements — 5 mandatory of 6 (4 functional, 2 compliance)
- R-01 Single sign-on with the Acme identity provider [4 Requirements, p.3]
- R-02 Model monitoring and drift alerts [4 Requirements, p.3]
- REQ-001 Ingest clinical data through FHIR R4 APIs … [3.1 Data Integration, p.2]
…plus 1 optional

### Compliance
- HIPAA: All components must align with HIPAA requirements [3.2 Compliance, p.2]
- HITRUST CSF: … [3.2 Compliance, p.2]
- CMS-0057: Support CMS-0057 interoperability rules … [3.2 Compliance, p.2]
📎 Download acme-2026-requirements-v1.xlsx
  • Requirement ids are checked. The RFP's own ids (R-01…) are kept only when the cited table row really has them; otherwise items are numbered REQ-001….
  • Conflicts are flagged, not guessed. Two different due dates become a red flag rather than a silent pick.
  • Typing /digest rebuilds it. Plain-text requests like "summarise the requirements" show the saved digest when it's up to date.

Build your block library

The deck writer tailors vetted blocks (reusable, client-neutral content from your past proposals), so it isn't inventing claims about your firm. Build the library once, then top it up.

  1. Put past proposals (PPTX, DOCX, PDF) in library/proposals/ and reference documents (standards, whitepapers) in library/reference/.
  2. Harvest, naming the old clients so they're anonymised: 
    /harvest Example Hospital, Old Client Inc
    Harvesting writes files, so if you ask in plain text it waits for your /approve.
  3. Review the YAML in library/blocks/<slide_type>/, edit it freely, and set needs_review: false when it's clean.

A harvested block. Client names, dates and amounts are replaced in Python after the model has done its own pass:

# Proposal Studio block. Edit freely: harvest never overwrites edited blocks.
id: complete-ai-platform-948060
slide_type: platform
title: Complete AI platform
body_points:
- Development workbench for notebooks, prompts, and evaluation
- MLOps and LLMOps pipelines with versioned models and prompts
- Observability for quality, drift, and cost
- Model registry with approvals and audit trail
tags: [llmops, mlops, model-registry, observability]
capability: AI platform
source_file: example_hospital_deck.pptx
source_ref: slide 3
needs_review: false
Your edits are safe Harvest never overwrites a block you've edited, even if you forgot to set edited: true (it compares content hashes). Re-harvesting only processes changed slides and sections.

Search blocks with /blocks mlops observability, and index the library for research with /library index.

Write the deck

/deck writes every slide in the outline: one model call per slide, using 2–4 of your blocks plus the digest facts relevant to that slide. /deck platform regenerates just one slide.

You
/deck
PS
→ routed to /deck (command)
Writing slide 2/11: understanding… · Writing slide 6/11: platform…
# Understanding Acme Health Plan's Challenges
- Care managers review claims and clinical notes manually in a legacy portal
- Prior authorization turnaround averages nine days

# Next Steps Timeline
- Weeks 1-2 — Conduct discovery workshops and set data access protocols
- Weeks 9-12 — Pilot implementation at Acme Health Plan, go/no-go review on March 15, 2027
Please review:
• understanding: not supported by the RFP facts: 'Leadership seeks AI solutions with strong governance frameworks'
• next_steps: a block's {{date}} may have been filled with March 15, 2027: check

The writer checks the model's output in Python:

  • Limits: one automatic "shorten" retry, then safe truncation, flagged.
  • Provenance: every slide records the blocks and RFP citations it used.
  • Review flags: figures or certifications found in neither your blocks nor the RFP, claims about the client the RFP doesn't support, and placeholder dates filled with unrelated values. These are flagged, not silently removed. That's your cue to /edit.
  • No invention: a slide about your firm with no vetted blocks becomes a visible skeleton ("Add content — no vetted blocks for why_us; run /harvest").

Use your own template

The renderer puts each slide into a layout from your template. Map it once:

  1. Copy your template (.pptx or .potx) into templates/. That folder is private and never committed.
  2. Inspect it: 
    .venv/bin/studio template inspect templates/firm.potx
    firm.potx: 13.33x7.5 in, 2 existing slides
  [0] Title Slide: 0=CENTER_TITLE, 1=SUBTITLE
  [1] Title and Content: 0=TITLE, 1=OBJECT
  [4] Comparison: 0=TITLE, 1=BODY, 2=OBJECT, 3=BODY, 4=OBJECT
  [5] Title Only: 0=TITLE
  3. Point each slide type at a layout and each field at a placeholder number in config/layout_map.yaml: 
    template: templates/firm.potx
remove_existing_slides: true
layouts:
  understanding: { layout: Title and Content, placeholders: { title: 0, bullets: 1 } }
  before_after:
    layout: Comparison
    placeholders: { title: 0, before_title: 1, before: 2, after_title: 3, after: 4 }
  solution_architecture: { layout: Title Only, placeholders: { title: 0 } }   # boxes drawn below the title
  why_us: { layout: Title and Content, placeholders: { title: 0, bullets: 1 }, limits: { bullet: 90 } }
  4. Test it with the sample deck: studio render --deck tests/fixtures/sample_deck.json --out build/.

Until you map your own, the neutral sample template in templates/sample/ is used.

📎 Download acme-2026-v1.pptx

What the renderer does, with no AI involved:

  • removes the template's own example slides;
  • fills placeholders, cutting overlong text at a word boundary and dropping extra bullets (all reported);
  • removes unused placeholders, so there's no "Click to add text";
  • draws the architecture slide as layered boxes;
  • puts each slide's sources in the speaker notes;
  • saves <opp>-v1.pptx, -v2… and never overwrites a file.

Research your library

For questions that need your past work and reference docs, not just the RFP:

/library index
/research How should we approach FHIR R4 integration and HIPAA safeguards for prior authorization?

Research is a short, bounded loop:

  1. split the question into sub-questions;
  2. search the RFP and both library collections with several phrasings;
  3. draft cited findings ([file, p.N] or [file, slide N]);
  4. search once more for weak findings;
  5. write a summary, implications for this RFP, and what the library doesn't cover.

Each run has a hard cap of 12 model calls (configurable). The report is saved to workspace/<opp>/research/ and offered as a download.

_offline · searched: RFP, Past proposals, Reference · 5 LLM calls_
### 1. What are the key technical requirements for FHIR R4 prior authorization?
_Evidence: strong_
- Payer prior authorization APIs build on FHIR resources … [fhir_r4_notes.pdf, p.2]
- The system must support CMS-0057 interoperability rules … [acme_rfp.pdf, p.2]
- HIPAA safeguards: encryption, access control, audit logging [example_hospital_deck.pptx, slide 4]

Agents

For file tasks like "tighten every bullet in deck.json", hand off to a local agent CLI. Install one while online: npm install -g opencode-ai and/or @anthropic-ai/claude-code (it runs against your local Ollama, never the cloud).

plan (throwaway copy)→/approve→apply in sandbox + diff→/approve→copy back
/agent opencode tighten the bullets on the platform slide in deck.json
  • Planning can't change anything. It runs in a copy that's deleted afterwards.
  • Apply runs in workspace/<opp>/agent/work, and you see a diff. Only the second approval copies changes back, and a changed deck.json must still be a valid deck.
  • Locked down by default: no shell, an isolated home folder, and no API keys or secrets passed in. Every run has a timeout and a log.
  • In the app, steps that change files show Run / Cancel buttons. Agent commands can only be changed in config/agents.yaml, never from chat.
Set expectations On a CPU-only laptop each step takes minutes, and small local models often don't use their file tools well. Keep tasks short and specific. Hermes Agent ships disabled until it has been verified offline.

Routing & confirmations

You can type commands or plain English. Each message is routed in this order, and the first line of the reply tells you which step decided:

StepExampleRoute line
1. A /command/digest→ routed to /digest (command)
2. Rules (no AI, instant)only attachments · "render the pptx" · "When are proposals due?"→ routed to /ask (rules)
3. Classifier (small model)"which slides will be in the deck"→ routed to /outline (classifier, 0.95)
4. Not sure"hmm, the thing from before""Did you mean /ask or /research?"
File-writing commands always wait /render, /harvest and /agent never run from plain text on their own. You get a confirmation dialog, or you can type /approve (alias /yes) or /reject (/no). Typing the command yourself runs it straight away. The PHI warning on ingest uses the same mechanism.

Configuration

Change settings from the chat. They're validated (unknown keys and cloud models are refused) and saved to config/overrides.yaml, which survives upgrades:

/config                                  # show effective settings
/config set worker.model qwen3:4b        # faster, slightly weaker writer
/config set auto_threshold 0.8           # router must be more confident
/config set top_k 8                      # more excerpts per /ask
/config reset                            # back to defaults

Privacy & data

Stays on your machine

Models (local Ollama, cloud models refused), the UI (offline mode, 127.0.0.1), embeddings, agents (local models, isolated, no keys passed). No telemetry in Proposal Studio's code.

Where your data lives

Each project in the folder you chose (RFPs, chats, decks, reports), plus the shared library/ in the Proposal Studio folder (shown in Settings). Keep them outside the repository. In the repository, workspace/, library/ and your templates/ are gitignored, and commit hooks block them.

Before using real documents

  • ☐ Your organisation permits these tools and models on this machine.
  • ☐ You start with scripts/start.*, so the offline environment is applied.
  • ☐ File Context is off for the Proposal Studio model.
  • ☐ The Ollama tray app isn't overriding the settings (Windows).
  • ☐ Real client files stay in your project folders and library, never in a repository.

The PHI scan and the anonymisation are safety nets, not de-identification tools. Details: docs/privacy.md.

Troubleshooting

Always start with studio doctor.

"Ollama isn't running" / "Model qwen3:8b isn't pulled"

Start Ollama (scripts/start.* does it), or ollama serve. While online, pull the missing model: ollama pull qwen3:8b.

The page says "Open Proposal Studio from its link"

The app only works from the http://127.0.0.1:8765/?t=… link that studio ui prints, which is new each launch. Open it again from the terminal, or restart with scripts/start.*.

"is a system folder" or "too broad" when choosing a project folder

Pick or create a folder for the bid, e.g. Documents\Bids\Acme. Whole drives, your home folder itself and system folders can't be used.

Where are my files?

The sidebar shows each project's path; the Files tab shows it in full with Open folder. Settings shows the Proposal Studio folder and library.

Port 8765 is already in use

Start on another port: studio ui --port 8766.

Answers repeat the same excerpt twice

The same RFP was ingested as both PDF and DOCX. Keep one format: remove one in the side panel's Files tab (or from projects/<project>/input/).

Slides say "Add content — no vetted blocks"

Build your library first: put past proposals in library/proposals/, run /harvest, review the YAML, and set needs_review: false.

Render QA errors about layouts

The mapping doesn't match your template. Run studio template inspect and fix config/layout_map.yaml. The error lists the template's layout names.

RAM fills up / several models loaded

Quit the Ollama tray app and let the start script launch Ollama so OLLAMA_MAX_LOADED_MODELS=1 applies. studio doctor warns when this happens.

Windows: "running scripts is disabled on this system"

Use powershell -ExecutionPolicy Bypass -File scripts\setup.ps1. It needs no admin rights.

More in docs/troubleshooting.md.

FAQ

Does any of my data go to the cloud?

No. At runtime everything talks to localhost: Ollama for the models and the Proposal Studio app for the UI. Cloud models are refused by name, and Ollama's cloud features are switched off. Internet is only used for setup.

Can I use a different or bigger model?

Yes: /config set worker.model <model> after ollama pull <model>. Bigger models need more RAM, and only one is loaded at a time. Cloud models (:cloud) are always refused.

Why does it flag things instead of fixing them?

Small local models sometimes import claims from a past client or invent a figure. Python checks catch these and show them to you. Silently deleting content could hide a real problem, and the final judgement should be yours.

Will it overwrite my files?

No. Renders and exports are versioned (-v1, -v2…), deck changes keep history, harvest never overwrites edited blocks, and agents only copy back after your second approval.

Can I use it without the browser?

Yes. studio chat is the same chat in a terminal, and every command also exists as studio <command>.

How do I upgrade?

Download the new release (or git pull), and re-run setup. Your project folders, the Proposal Studio folder, templates/ and config/overrides.yaml are kept.

Glossary

Project / opportunityOne bid you're working on, in its own folder (chosen by you in the app; workspace/<id>/ in the CLI) holding the RFP files, index, digest, deck and renders.
DigestThe structured, cited summary of the RFP (digest.json) that feeds the outline and the deck.
BlockA reusable, client-neutral piece of content (title + points + tags) harvested from past proposals and curated by you.
Storyline / outlineThe fixed deck spine (storyline.yaml), and the per-RFP decision of which slides are in (outline.json).
ProvenanceThe blocks and RFP citations a slide was built from, kept in deck.json and the speaker notes.
Review flagSomething a person should check: an unsupported claim, a figure from nowhere, a filled placeholder, a truncation.
Proposal Studio folderHolds the shared library and the list of your projects; new projects go here by default. Shown in Settings.
Router role / worker roleThe small model that routes messages (qwen3:4b), and the model that writes and extracts (qwen3:8b).
